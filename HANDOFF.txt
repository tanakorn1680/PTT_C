HANDOFF — พอร์ตเกม Prototype (PC 2009) เป็น APK native ด้วยการแปลง DLL เป็น C
(ไฟล์นี้ไว้ส่งต่อให้ AI ตัวอื่นทำต่อ — อัปเดตทุกครั้งที่ส่งงานใหม่)
อัปเดตล่าสุด: 2026-10-23 (รอบที่ 3)

== เป้าหมาย ==
- ทำ APK Android (arm64) ที่รัน Prototype (Radical Entertainment, 2009) แบบ native
  ด้วยแนวทาง static recompilation เหมือนโปรเจกต์ codepdbh/nfsu2-recompiled
  (x86 -> C ด้วย pcrecomp -> compile ด้วย NDK; กราฟิก D3D9 -> Vulkan ผ่าน DXVK)
- ผู้ใช้มีไฟล์เกมของแท้ และต้องการประสิทธิภาพสูงสุด (ห้ามใช้ตัวจำลอง/emulator เช่น Winlator, Box64)

== ข้อจำกัดของผู้ใช้ / วิธีทำงาน ==
- มีแต่มือถือ Android ไม่มีคอม ใช้ GitHub Actions (repo ต้อง private)
- สื่อสารภาษาไทย
- ส่งงานเป็น ZIP เฉพาะไฟล์ที่เปลี่ยน โครงโฟลเดอร์ตรงกับ root ของ repo (แตกทับได้เลย)
- ไม่ต้องทดสอบ/ทำอะไรเกินจำเป็น; บันทึกความคืบหน้าไว้ในไฟล์นี้ทุกครั้ง
- ผู้ใช้เปลี่ยนชื่อ DLL เป็น game/engine.dll ใน repo (workflow เลือก .dll ที่ใหญ่สุดใน game/)
  ในโฟลเดอร์เกมจริงต้องใช้ชื่อเดิม (prototypeenginef.dll)
- AI ที่ทำงานในแชตไม่มีเน็ต (ดึง pcrecomp/NDK ไม่ได้) => ทดสอบจริงได้แค่บน GitHub Actions
  ผู้ใช้เป็นคนรัน workflow แล้วส่ง artifact "lift-report" กลับมา

== ข้อมูลที่ยืนยันแล้ว (จากการตรวจไฟล์) ==
- prototypef.exe = ตัวเปิด (launcher) โค้ดจริงราว 8KB; โหลด DLL ของ engine แล้วเรียก export
  (EngineInitialize, EngineService, EngineTerminate, EngineWindowFocus, EngineMouseService,
   EngineKeyboardService, MainWin32). ชื่อ DLL ที่ exe โหลดยังไม่ยืนยัน (เดาจากสตริง "f.dll")
  แนวทางที่เสนอ: ไม่ lift exe แต่เขียน launcher ใหม่ฝั่ง host เรียก export เหล่านี้เอง
- prototypeenginef.dll: PE32 x86, 20.2MB, build 2009-04-22, MSVC 2005 (MSVCR80), ไม่ถูกห่อ/เข้ารหัส,
  ไม่พบสตริง SecuROM/StarForce/Steam, ไม่ใช่ large-address-aware, มี relocation table, image base 0x10000000
- import: d3d9 (แค่ Direct3DCreate9), DirectSound, WINMM waveOut, XINPUT1_3, WS2_32,
  binkw32.dll (วิดีโอ Bink ปิดซอร์ส -> ต้อง stub/ข้ามบน Android)
- Scaleform GFx (UI) ลิงก์อยู่ใน DLL, มีสคริปต์ Lua ในตัวเกม, .text ราว 14MB

== ผล bench compile ARM64 (รันบน Actions จริง 2026-10-23, รันเนอร์ 4 คอร์ / 16GB, NDK clang 21) ==
- ตัวอย่าง 6 ไฟล์ compile ผ่านทั้งหมด (rc=0) ด้วยแฟล็กเดียวกับ nfsu2 (-O2 ไม่มี LTO) => โค้ดที่ lift compile ได้จริง
- ไฟล์ปกติ ~0.3-1 MB ใช้ 1.3-2.9 วินาที/ไฟล์ RAM ~150-200 MB (ประมาณ 2.9 วินาที/MB)
- **ผิดปกติ: recomp_0327.c ใหญ่ 87 MB (ทั้งหมด 626 MB) ใช้ 518 วินาที และ RAM พีค ~8 GB** ไฟล์เดียวเกือบ 1/7 ของข้อมูลทั้งหมด
  น่าจะมีฟังก์ชันขนาดมหึมา 1 ตัวหรือไม่กี่ตัว (เช่นตารางข้อมูลที่ถูกถอดเป็นโค้ด) -> เป็นคอขวดของ build
- ตัวเลข "~15 นาที" ใน bench.txt ถูกบิดเบือนจากไฟล์ใหญ่นี้; ประมาณจริง: ไฟล์ปกติรวม ~540MB x 2.9s/MB ~ 26 CPU-นาที (~7 นาทีบน 4 คอร์)
  + ไฟล์ 0327 อีก ~9 นาที (เธรดเดียว) ถ้าไม่ถูกแก้
- ยังไม่ได้วัด ThinLTO link (nfsu2 เปิดไว้) กับ 13.6M บรรทัดอาจกิน RAM/เวลามาก

== งานที่ทำในรอบที่ 3 (ส่งในซิปนี้) ==
- patches/ptt_lifter_ext.py + patches/ptt_lift_ext_src.py: ตัวแปะ lift32.py ของ pcrecomp ตอนรันบน CI (ต่อจาก git am)
  * เพิ่ม fcomi/fucomi/fcompi/fucompi: ใช้โมเดลเดียวกับสาขา fcomip เดิม (FPU_CMP + สถานะแฟล็ก 'fcom') แต่ใช้ตัวถูกดำเนินการ st(i) จริง
  * เพิ่ม lock xadd / lock cmpxchg (dword, ปลายทางเป็นหน่วยความจำ) / lock cmpxchg8b: ไม่ใช้ atomic เพราะเธรด guest รันภายใต้ machine lock;
    แฟล็กตั้งเป็นภาพ EFLAGS (FK_EFLAGS) คำนวณในโค้ดที่สร้างเอง (CF PF AF ZF SF OF) ไม่พึ่งฟังก์ชันของ runtime
  * ตรวจแล้วบนเครื่อง AI: C ที่สร้างสำหรับ xadd/cmpxchg/cmpxchg8b คอมไพล์ด้วย gcc และตรงกับตัวอ้างอิง Python 6,000/6,000 ชุดสุ่ม
    (ผลลัพธ์ + แฟล็ก); ตัวแปะ lift32/difftest ทดลองบนไฟล์จำลองแล้ว syntax ผ่าน; **ยังไม่ได้รันกับ pcrecomp จริง**
  * ฟอร์มที่ไม่ตรงเงื่อนไข (ไม่ใช่ 32-bit / ปลายทางไม่ใช่ memory) ยังตกไป RECOMP_UNIMPL เหมือนเดิม (ดังชัด ไม่เงียบ)
  * ตัวแปะจะ fail ดังๆ ถ้า anchor ไม่เจอหรือแปะซ้ำ; เพิ่มเคส difftest 12 เคสให้ difftest.py (ถ้าหา anchor เจอ)
- workflow lift-prototype.yml: เพิ่มขั้น Apply extension, difftest (informational, อาจต้องปรับแฟล็ก ดู work/difftest.log),
  compile-check (compile -fsyntax-only ไฟล์เล็กที่มีคำสั่งใหม่ + นับ RECOMP_UNIMPL ที่เหลือ), และ big_functions.txt
  (ไฟล์/ฟังก์ชันที่ใหญ่สุด: address+ขนาด ไม่มีโค้ด); bench ปิดเป็นค่าเริ่มต้นแล้ว (ผลได้แล้ว; ไฟล์ใหญ่สุดกิน ~9 นาที/8GB)
- scripts/compile_check.sh, scripts/lift_diagnostics.py (เพิ่ม big_functions)
- สิ่งที่คาดหวังจากการรันครั้งหน้า: unimplemented_total ลดจาก 4,421 เหลือ ~45, lift_failures ยัง 0, compile-check ผ่าน

== ขั้นต่อไปที่วางไว้ ==
1) ผู้ใช้แตกซิป รัน workflow "Lift game DLL to C" (ไม่ต้องติ๊ก bench) แล้วส่ง artifact lift-report กลับมา
   ดู: lift_stats.json (unimplemented เหลือเท่าไร), compile_check.txt, difftest.log, big_functions.txt
2) ถ้า difftest.log ล้ม/ใช้แฟล็กไม่ถูก: ดูส่วน --help ในไฟล์แล้วปรับคำสั่งใน workflow; ถ้ามีเคส ptt.* ไม่ผ่าน ต้องแก้ ptt_lift_ext_src.py
3) แก้ไฟล์ยักษ์ recomp_0327.c: ดู big_functions.txt ว่าฟังก์ชันไหนใหญ่; ถ้าเป็นข้อมูลไม่ใช่โค้ดให้ใส่ใน exclude.txt
   (รูปแบบเดียวกับ nfsu2: lift/config/exclude.txt, ใช้ "excluded: not code") แล้ว lift ใหม่ หรือแยกไฟล์ด้วยแบบ scripts/split_android_sources.py ของ nfsu2
   (แยกที่ขอบเขตฟังก์ชัน; ไม่ช่วยถ้าเป็นฟังก์ชันเดียวขนาดมหึมา)
4) ตรวจ bsr / fisttp / fcmovb / fcmovnbe (จุดที่น่าจะเป็นโค้ดจริง) และเพิ่มถ้าจำเป็น
5) วัด ThinLTO link กับตัวอย่างจริง และตัดสินใจแฟล็ก (-O2/-O1, LTO on/off, จำนวน job ขนาน)
6) ออกแบบ host layer (เริ่มจาก nfsu2-recompiled/android): PE loader ของ DLL (base 0x10000000, relocation, IAT),
   Win32 HLE ที่ DLL ใช้, D3D9 -> DXVK (Direct3DCreate9 อย่างเดียว), DirectSound/waveOut -> AAudio,
   XInput/ทัช, stub binkw32 (ข้ามวิดีโอ), launcher ฝั่ง host เรียก Engine* exports (ไม่ lift exe)
7) ตั้ง Gradle/NDK build บน Actions (อิง android/ ของ nfsu2: NDK 28.2.13676358, SDK 35, CMake 3.30.5);
   host/arm64_guest.h ใช้เป็น -include ได้เลย
